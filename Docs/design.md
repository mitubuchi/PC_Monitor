# PCMonitor 設計書

常駐型のキーロガーとバックドアの「疑わしい候補」を洗い出す、Windows 用の点検ツール。

- 作成日: 2026-11-13
- 状態: 第 1 段階を実装済み（2026-11-13）。第 2 段階は、親子関係の異常・読み込み DLL・メモリの点検まで（§11）。
  ETW によるキー入力 API の監視が残っている
- 名前: はじめ `Security` としていたが、フォルダー名に合わせて `PCMonitor` に揃えた
  （隣の AgentMonitor との取り違えと、`System.Security` との紛らわしさを避ける）

## 1. 目的と位置づけ

Windows Defender を**置き換えない**。Defender が見ない観点を補う点検ツールとする。

- Defender はシグネチャと挙動で「既知の悪いもの」を止める
- PCMonitor は「常駐している・通信している・署名が無い」といった**条件の重なり**を見て、
  人が確認すべきものを危険度順に並べる

判定は「疑わしい候補」までで、「これはウィルスだ」とは断定しない。
キーロガーもバックドアも、使う仕組みは正規ソフト（IME、AutoHotkey、リモートデスクトップ系）と
同じなので、仕組みだけでは区別できないため。

## 2. 範囲

### やること

| 段階 | 内容 |
|---|---|
| 第 1 段階 | 常駐箇所の点検、プロセスの署名と起動場所の点検、通信の点検、WPF 画面、許可リスト、書き出しと前回との差分 |
| 第 2 段階 | メモリの点検（インジェクションの痕跡）、読み込み DLL の点検、ETW によるキー入力 API の監視 |

### やらないこと

| やらないこと | 理由 |
|---|---|
| リアルタイム保護（開いた瞬間に止める） | カーネルのミニフィルタードライバーと Microsoft の署名が要る |
| 削除・隔離・プロセスの強制終了 | 誤検知で正規ソフトを壊す。ツールは「見つけて示す」まで |
| 検体のアップロード（VirusTotal など） | 手元のファイルを外部へ送ることになる。ハッシュをコピーして本人が調べる |
| カーネルレベルのルートキットの検知 | ユーザーモードからは、隠されたものが見えない |

## 3. 対象とする手口

### キーロガー

| 手口 | 第 1 段階での見つけ方 | 第 2 段階での見つけ方 |
|---|---|---|
| キーボードフック（`SetWindowsHookEx` の `WH_KEYBOARD_LL`） | 間接的な兆候のみ（下記） | ETW で設置の瞬間を捕まえる |
| ポーリング（`GetAsyncKeyState` を高頻度で呼ぶ） | 間接的な兆候のみ | ETW で呼び出し元を特定する |
| Raw Input の登録（`RegisterRawInputDevices`） | 間接的な兆候のみ | ETW で登録の瞬間を捕まえる |

設置済みのフックを列挙する公式 API は無い。第 1 段階では、次の兆候の重なりで候補に挙げる。

- 自動起動に登録されている
- ウィンドウを表示しないのに常駐している
- 未署名である
- ユーザーが書き込める場所（`AppData`、`Temp` など）から起動している

### バックドア

通信と常駐の両方が要るので、キーロガーより手がかりが多い。

- 未署名のプロセスが、ループバック以外でポートを待ち受けている
- 未署名のプロセスが、外向きの接続を持ち続けている
- 自動起動の登録が、スクリプト実行系の正規ツール（`powershell -enc`、`mshta`、`rundll32`、
  `regsvr32` など）を経由している
- システムのプロセス名を名乗っているが、置き場所が違う（`System32` 以外の `svchost.exe` など）

## 4. 全体構成

```
PCMonitor/
  ├─ Docs/design.md              この文書
  ├─ PCMonitor.sln
  ├─ src/
  │   ├─ PCMonitor.Core/         点検ロジック。UI に依存しない
  │   ├─ PCMonitor.Cli/          コンソール版（pcmonitor.exe）。画面なしで点検を走らせる
  │   └─ PCMonitor.Wpf/          画面（WPF + ReactiveUI）。実行ファイルは PCMonitor.exe
  └─ tests/
      ├─ PCMonitor.Core.Tests/   採点と解析の単体テスト
      └─ PCMonitor.Probe/        検知を実測するための無害な検証プログラム（§12）
```

| プロジェクト | TargetFramework | 備考 |
|---|---|---|
| `PCMonitor.Core` | `net9.0-windows` | Win32 API を P/Invoke で呼ぶ。Nullable `enable` |
| `PCMonitor.Cli` | `net9.0-windows` | 検知の実測に使う。定期実行を足すときの入口にもなる |
| `PCMonitor.Wpf` | `net9.0-windows10.0.19041.0` | ReactiveUI は **23.2.28 に固定**（ReactiveUI.WPF がこの TargetFramework 向け）。`StartupUri` は使わず `App.xaml.cs` で手動初期化 |

点検ロジックを `Core` に分けるのは、コンソール版や定期実行（タスクスケジューラから
起動して差分だけ通知する）を足せるようにするため。コンソール版は、画面を作る前に
検知を実測するために先に作った。

```
pcmonitor [--min-level info|low|medium|high] [--verbose] [--find <文字列>]
          [--json <パス>] [--csv <パス>] [--data-dir <フォルダー>] [--no-save]
pcmonitor --verify <ファイル>      署名の検証結果だけを表示する
```

### Core の中の分け方

```
PCMonitor.Core/
  ├─ Collectors/     事実を集める（判断しない）
  │   ├─ PersistenceCollector   常駐箇所
  │   ├─ ProcessCollector       プロセス
  │   └─ NetworkCollector       通信
  ├─ Signing/        署名の検証
  ├─ Scoring/        集めた事実に兆候を付け、危険度を決める
  ├─ Allowlist/      許可リスト
  └─ Reports/        書き出しと差分
```

**集める**と**判断する**を分ける。採点の規則はあとで必ず調整することになるので、
事実の取得を巻き込まずに直せるようにしておく。

## 5. 点検項目（第 1 段階）

### 5.1 常駐箇所

| 箇所 | 読む場所 |
|---|---|
| Run / RunOnce | `HKLM` と `HKCU` の `Software\Microsoft\Windows\CurrentVersion\Run`・`RunOnce`。`WOW6432Node` 側も見る |
| スタートアップ フォルダー | ユーザーごと、および全ユーザー共通。`.lnk` はリンク先まで解決する |
| サービス | `HKLM\SYSTEM\CurrentControlSet\Services`。`ImagePath` と、`svchost` 経由なら `Parameters\ServiceDll` |
| タスクスケジューラ | Task Scheduler の COM インターフェイスで列挙し、実行するコマンドを取る |
| WMI イベント購読 | `root\subscription` の `__EventFilter`・`CommandLineEventConsumer`・`ActiveScriptEventConsumer`・`__FilterToConsumerBinding` |
| Winlogon | `Shell`・`Userinit` が既定値から変わっていないか |
| `AppInit_DLLs` | 値が入っていれば挙げる |
| IFEO | `Image File Execution Options` の `Debugger` 値 |

登録されたコマンドラインから**実行ファイルのパスを取り出す**処理が要になる。
引用符の有無、環境変数、`rundll32 xxx.dll,Entry` のような間接起動を解いて、
実際に動くファイルまでたどる。たどれなかったものは「解決できず」として挙げる（隠さない）。

実装して分かったこと:

- タスクの動作が COM ハンドラーのときは、`CLSID` の `InprocServer32`・`LocalServer32`、
  無ければ `AppID` の `LocalService`（サービスが受け持つ形）までたどる。
  パッケージ化されたアプリの COM クラスはレジストリに無いので、「解決できず」に残る
- 引用符が二重に付いた登録（`""C:\…\x.exe"" -arg`）が実在する。タスク スケジューラは受け付ける
- サービスは `Start` が 2 以下（ブート・システム・自動）だけを自動起動として数える。
  手動と無効は、登録として載せるが点は付けない。Run キーとスタートアップも、
  タスク マネージャーで無効にされたもの（`StartupApproved`）は同じ扱い
- ドライバーも対象に入れた（常駐箇所として同じ意味を持つ）

### 5.2 プロセス

| 取るもの | 取り方 |
|---|---|
| 一覧と親プロセス | Toolhelp スナップショット |
| 実行ファイルのパス | `QueryFullProcessImageName`（`PROCESS_QUERY_LIMITED_INFORMATION` で足りる） |
| コマンドライン | WMI の `Win32_Process` |
| 表示中のウィンドウの有無 | `EnumWindows` と `IsWindowVisible` |
| 署名 | §5.4 |
| ファイルの作成日時・ハッシュ（SHA-256） | ファイルから |

### 5.3 通信

| 取るもの | 取り方 |
|---|---|
| TCP の待ち受けと接続（プロセス ID 付き） | `GetExtendedTcpTable`（IPv4 と IPv6） |
| UDP の待ち受け（プロセス ID 付き） | `GetExtendedUdpTable`（IPv4 と IPv6） |

スナップショットなので、**点検した瞬間に張っていない接続は見えない**。
一定間隔で通信するバックドアを見逃しうる。第 1 段階では「待ち受け」を主な手がかりとし、
外向き接続は補助に留める。

- UDP のバインドは事実として載せるだけで、**点は付けない**。DNS を引くだけのプロセスも
  `0.0.0.0` にバインドするので、「待ち受け」として数えると区別が付かない
- 外向きか内向きかは、スナップショットからは直接は分からない。そのプロセスが
  待ち受けているポートで受けた接続を除いた残りを、外向きとして数える

### 5.4 署名の検証

`WinVerifyTrust` を使う。**埋め込み署名だけでなく、カタログ署名も必ず確かめる。**
Windows 付属のファイルの多くはカタログ署名で、埋め込み署名を持たない。
これを見落とすと、`System32` の中身が軒並み「未署名」と出て、結果が使いものにならなくなる。

結果は 4 通りに分ける。

| 結果 | 意味 |
|---|---|
| 有効（Microsoft） | 署名が有効で、発行元が Microsoft |
| 有効（その他） | 署名が有効。発行元の名前を表示する |
| 無効 | 署名はあるが検証に失敗（改ざん・期限切れ・信頼されない発行元） |
| 無し | 署名が無い |

ファイルが無い・読めないときは「検証できず」とし、点は付けない。

**MSIX（ストア アプリ）の中のファイル**は、埋め込み署名もカタログ署名も持たないのがふつうで、
そのままでは「無し」になる。署名はパッケージ全体に 1 つなので、3 段でたどって確かめる。

1. `AppxSignature.p7x` の署名が有効か（`WinVerifyTrust`）
2. p7x が保証している `AppxBlockMap.xml` のハッシュ（`AXBM`）が、実際のファイルと合うか
3. 対象のファイルの中身が、`AppxBlockMap.xml` のブロック（64 KB）ごとのハッシュと合うか

**失効の確認はしない**（`WTD_REVOKE_NONE`）。数百のファイルを点検するたびに発行元へ
問い合わせることになり、ネットワークに出ない方針とも合わないため。
失効した証明書で署名されたものは「有効」と出る。

「Microsoft」の判定は、署名者の証明書の組織名（`O=`）が `Microsoft Corporation` であること。

**署名が有効でも安全とは限らない**（正規ツールの悪用、盗まれた証明書）。
署名は「減点の材料」であって「無罪の証明」ではない。

## 6. 危険度の採点

事実に**兆候**を付け、点数を足して危険度を決める。点数は初期値で、実機で試しながら調整する。

| 兆候 | 点 |
|---|---|
| 署名が無効 | +50 |
| システムのプロセス名を名乗るが、置き場所が違う | +40 |
| 自動起動がスクリプト実行系の正規ツールを経由している | +40 |
| 署名が無い | +30 |
| ふつうは使われない常駐箇所（Winlogon・AppInit_DLLs・IFEO・WMI イベント購読）に登録されている | +30 |
| ユーザーが書き込める場所から起動している | +20 |
| ループバック以外でポートを待ち受けている | +20 |
| 隠し属性が付いている、または拡張子が二重（`.pdf.exe` など） | +15 |
| 自動起動に登録されている | +10 |
| 外向きの接続を持っている | +10 |
| 表示中のウィンドウが無い | +10 |
| ファイルの作成日時が 7 日以内 | +10 |

| 危険度 | 点 |
|---|---|
| 高 | 60 以上 |
| 中 | 30〜59 |
| 低 | 10〜29 |
| 情報 | 9 以下 |

- 兆候は 1 つずつでは弱い。**重なったときに上がる**ように、単独で「高」になるものは作らない
- 「登録は残っているが、ファイルが無い」は点を付けず、情報として挙げる
- 同じ実行ファイルが常駐・プロセス・通信の 3 か所に出てきたら、**1 件にまとめて**兆候を合算する
  （パスで突き合わせる）。まとめないと、同じものが 3 行に分かれて危険度が低く見える
- ファイルにたどり着かない登録（`powershell -enc …` のように、その場に書かれた命令）は、
  登録ごとに 1 件とする。許可リストのハッシュは、命令の文字列から取る
- 点検している自分自身は候補にしない

### 実機で試して決めた適用の条件（2026-11-13）

点数は表のままで、**どういうときに付けるか**を絞った。どれも、絞らないと正規のものが
大量に挙がって、見るべきものが埋もれた。

| 兆候 | 条件 | 絞らなかったときに起きたこと |
|---|---|---|
| 作成日時が 7 日以内 | 署名が有効なファイルには付けない | Windows Update の 2 日後に、580 件が「新しい」になった |
| スクリプト実行系を経由 | 対象のファイルまでたどれて、その署名が有効なら付けない | Windows 自身のタスク（`cmd /c …\hpatchmonTask.cmd` など）が「中」になった |
| 署名が無い | スクリプト（`.ps1`・`.bat`・`.vbs` など）には付けない | スクリプトはふつう署名を持たない。「スクリプト経由」と二重に数えることになる |
| 表示中のウィンドウが無い | 点検する側と同じセッションのプロセスだけで見る | セッション 0（サービス）のウィンドウは元々見えないので、サービスがすべて該当する |
| ユーザーが書き込める場所 | フォルダーの名前ではなく、**ファイルのアクセス許可**で決める（管理者でない利用者に書き込みが許されているか）。ほかの利用者のプロファイルと `Windows\Temp` は、名前で該当とする | `ProgramData` の下には、守られた場所（Defender）と書き換えられる場所（一部のメーカー製ツール）が混じっている |
| 登録は残っているが、ファイルが無い | 自動起動の点も付けない | 起動できない登録が「低」になる |

この PC の素の状態（通常の権限）での結果: 高 0、中 9、低 419、情報 525。所要 2〜3 秒。
「中」は、`AppData` から動く常駐アプリ（Ollama・Zoom・Claude Code）と、常駐して通信する
同期アプリ（OneDrive・pCloud）だった。

## 7. データモデル

```
Finding（1 件の候補）
  ├─ Path            実行ファイルのパス（まとめる単位）
  ├─ Sha256
  ├─ Signature       結果と発行元
  ├─ Indicators[]    付いた兆候（種類・点・根拠の文）
  ├─ Score / Level   合計点と危険度
  ├─ Persistence[]   どの常駐箇所に、どんなコマンドラインで登録されているか
  ├─ Processes[]     プロセス ID・親・コマンドライン・ウィンドウの有無
  └─ Endpoints[]     プロトコル・ローカルのアドレスとポート・相手先・状態
```

兆候には**根拠の文**を必ず持たせる（「`HKCU\...\Run` の `Updater` に登録」など）。
点数だけ出しても、人は確認のしようがない。

## 8. 画面

1 つのウィンドウに、上から「操作」「一覧」「詳細」を並べる。

```
┌──────────────────────────────────────────────────────────┐
│ [スキャン] [管理者として再起動]   種別 ▼  危険度 ▼  検索 │
│ 進捗: 通信を点検中…                 □ 許可済みも表示     │
├──────────────────────────────────────────────────────────┤
│ 危険度 │ 名前        │ 署名     │ 兆候            │ 点  │
│ 高     │ updater.exe │ 無し     │ 常駐 待受 未署名│ 70  │
│ 中     │ …           │          │                 │     │
├──────────────────────────────────────────────────────────┤
│ 詳細: パス / SHA-256 / 署名者 / 作成日時                 │
│ 根拠: ・HKCU\…\Run の「Updater」に登録                   │
│       ・0.0.0.0:4444 を待ち受け                          │
│ [ファイルの場所を開く] [ハッシュをコピー] [許可リストへ] │
└──────────────────────────────────────────────────────────┘
```

- **一覧**: 既定は危険度の高い順。種別（常駐・プロセス・通信）と危険度で絞り込める
- **詳細**: 選んだ項目の根拠を文で並べる
- **操作**: 「ファイルの場所を開く」「ハッシュをコピー」「許可リストへ追加」だけ。壊す操作は置かない
- **書き出し**: CSV と JSON
- **前回との差分**: 前回の結果と比べ、新しく増えた項目に印を付ける

スキャンは別スレッドで走らせ、途中で止められるようにする。項目ごとの失敗（権限不足など）は
全体を止めず、「この項目は点検できなかった」として画面に出す。

## 9. 権限

| 権限 | 見られる範囲 |
|---|---|
| 通常 | 常駐箇所の大半、自分のプロセス、通信の一覧 |
| 管理者 | 上に加えて、他ユーザーとシステムのプロセスのパス、一部のタスク、WMI イベント購読 |

- 通常権限でも起動でき、**見られる範囲だけ点検する**。マニフェストで昇格を強制しない
- 見られなかった項目は、件数とともに「管理者なら見られる」と表示する
- 「管理者として再起動」ボタンで昇格する

## 10. 保存するもの

置き場所は `%LOCALAPPDATA%\PCMonitor\`。どれも JSON（UTF-8、BOM 無し）。
書き出す CSV だけは BOM を付ける（Excel で開くと日本語が化けるため）。

| ファイル | 中身 |
|---|---|
| `allowlist.json` | 許可リスト |
| `last-scan.json` | 前回の結果（差分に使う） |

### 許可リスト

**パスとハッシュの組**で登録する。パスだけで許可すると、同じ場所のファイルを
差し替えられても気づけない。ハッシュが変わったら許可は外れ、
「許可済みだったが中身が変わった」として挙げる（更新でも変わるので、危険度は上げない）。

## 11. 第 2 段階

| 項目 | 状態 | 内容 |
|---|---|---|
| 親子関係の異常 | 実装済み（2026-11-13） | 文書を開くアプリがシェルを起動している。システムのプロセスの親が決まった相手ではない |
| 読み込み DLL の点検 | 実装済み（2026-11-13） | 署名済みのプロセスに読み込まれた、署名の有効でない DLL |
| メモリの点検 | 実装済み（2026-11-13） | `VirtualQueryEx` で、ファイルの裏付けが無い実行可能な領域を探す（インジェクションの痕跡）。JIT を持つプロセスは見ない（§11.3） |
| ETW によるキー入力 API の監視 | 調査中（§11.5） | Win32k のプロバイダーで、`SetWindowsHookEx`・`GetAsyncKeyState`・`RegisterRawInputDevices` の呼び出し元を記録する。管理者権限が要る |

⚠️ ETW のイベント番号と取れる項目は、**実機で確かめてから設計に書く**。
Windows の版で変わりうるので、記憶で決めない。定義を読んだ結果は §11.5。

### 11.1 親子関係の異常

| 見るもの | 点 | 理由 |
|---|---|---|
| 文書を開くアプリ（Word・Excel・Outlook・PDF リーダーなど）が、シェルやスクリプト実行系（`cmd`・`powershell`・`wscript`・`mshta`・`rundll32` など）を起動している | +30 | マクロや細工した文書が命令を実行するときの形 |
| システムのプロセスの親が、決まった相手ではない（`svchost.exe`・`spoolsv.exe` の親は `services.exe`、`services.exe`・`lsass.exe` の親は `wininit.exe`、`taskhostw.exe`・`RuntimeBroker.exe`・`sihost.exe` の親は `svchost.exe`） | +30 | 正規のプロセスを起動して中身を差し替える手口では、親が決まった相手にならない。第 1 段階では見えなかった「正規プロセスへのインジェクション」の入口のひとつ |

- 点は、**起動された側**（子）の実行ファイルに付ける。根拠の文に、親と子の名前とプロセス ID を出す
- **親の番号は使い回される。** 親が終わったあと、同じ番号が別のプロセスに付く。
  実機でも `csrss.exe` と `winlogon.exe` の親が `svchost.exe` に見えていた（本当の親の `smss.exe` はもう居ない）。
  起動時刻が分かるときは、親のほうが先に起動していることを確かめる
- `services.exe` と `wininit.exe` は Windows が動いている間ずっと居るので、番号は使い回されない。
  この 2 つが親であるはずのものは、起動時刻が分からなくても（管理者でなくても）食い違いを異常と言える。
  親が見つからないことも異常として挙げる。親が `svchost.exe` であるはずのものは、起動時刻が分かるときだけ判定する
- **ブラウザーは「文書を開くアプリ」に入れない。** 拡張機能のネイティブ メッセージングが
  `cmd.exe` 経由で起動するのは正規の動きで、実機でも `chrome.exe → cmd.exe` が出ていた
- 親の表は 2026-11-13 にこの PC で確かめた（`svchost.exe` 89 個すべての親が `services.exe`、ほかも表のとおり）

### 11.2 読み込み DLL の点検

**集め方**: プロセスが自分で持っている DLL の一覧（PEB）は読まない。そこは本人が書き換えられるので、
名前を偽ったり、一覧から外したりできる。代わりに `VirtualQueryEx` でアドレス空間を端から歩き、
イメージとして割り当てられた領域ごとに、カーネルが覚えているファイル名を `GetMappedFileName` で聞く。

- 要るのは `PROCESS_QUERY_INFORMATION` だけ。**ほかのプロセスのメモリの中身は読まない**
- 返ってくるのは `\Device\HarddiskVolume3\…` の形なので、`QueryDosDevice` でドライブ文字に直す
- この歩き方は、次の「メモリの点検」（ファイルの裏付けが無い実行可能な領域）でもそのまま使える

**候補にするもの**: 署名が有効なプロセスに載っている、署名が「無し」か「無効」の DLL。

| 兆候 | 点 |
|---|---|
| 署名が無い（DLL としてだけ出てきたもの） | +10 |
| 署名済みのプロセスに読み込まれている | +10 |
| 発行元の違う 3 社以上のプログラムに読み込まれている | +15 |

これに、ファイルの兆候（書き込める場所 +20、作成日時 +10、署名が無効 +50）が重なる。

- **「署名が無い」は、実行ファイルの +30 ではなく +10。** 署名済みの本体に未署名の DLL を同梱する製品は多く、
  同じ +30 だと 1 つの製品（この PC では pCloud）で 39 件が「中」になった。自動起動や通信にも出てきた DLL は +30 のまま
- **本体が未署名のアプリの DLL は挙げない。** DLL も未署名なのがふつうで、本体のほうがもう挙がっている
- **「発行元の違う 3 社以上」**は、キーボード フック（`WH_KEYBOARD`）のように、ほかのプロセスへ入り込む DLL の形。
  プログラムの数ではなく発行元の数で数える（Git のように、同じ製品の複数の EXE が同じ DLL を使うのは別の話）。
  第 1 段階では間接的な兆候しか無かったキーロガーに対する、いちばん直接の手がかり
- **`%SystemRoot%\assembly\NativeImages_*` は挙げない。** .NET Framework がその PC の上で作る実行用の写し（NGEN）で、
  署名の付けようがない。この PC では 42 件あった。管理者でなくても書き換えられる状態になっていたら挙げる
- 署名を確かめるファイルが数千に増えるので、ハッシュまで取るのは署名が有効でなかったものだけにする。
  この PC では点検全体で 2〜3 秒が 4 秒弱になった

### 11.3 メモリの点検

§11.2 と同じ歩き方で、**実行できるのに、実行イメージではない領域**を集める。2 種類ある。

- **ファイルの裏付けが無い領域**（`MEM_PRIVATE`）。プロセスがその場で確保したメモリ
- **ファイルを写しただけの領域**（`MEM_MAPPED`）。DLL として読み込んだのではなく、
  データとして写したファイル（またはページ ファイル上の共有メモリ）が、実行できるようになっている

ここでも**メモリの中身は読まない**。分かるのは、領域の場所・大きさ・保護（実行できるか、書き込めるか）だけ。

**除外の扱い**: 実行時にコードを作る仕組み（JIT）を持つプロセスは、こうした領域を正規に作る。
インジェクションと区別できないので、**JIT を持つプロセスでは見ない**。JIT の有無は 2 通りで見分ける。

| 見分け方 | 対象 |
|---|---|
| 読み込んでいる DLL の名前 | .NET（`clr.dll`・`coreclr.dll`・`clrjit.dll`）、Java（`jvm.dll`）、Chrome・Edge・WebView2・CEF（`chrome.dll`・`msedge.dll`・`libcef.dll`）、Firefox（`xul.dll`）、Chakra、Qt QML、LuaJIT |
| EXE が外に公開しているシンボル（ディスク上のファイルから読む） | JIT を EXE に内蔵したもの。Node.js・Electron・Bun・Deno はネイティブ アドオン向けに `napi_*` を、.NET の単一ファイル アプリは `DotNetRuntimeInfo` を公開している |

2026-11-13 の実測（通常の権限、割り当てを見られた 106 個のプロセスのうち 43 個が該当）:

| 分類 | プロセス | ようす |
|---|---|---|
| JIT の DLL あり | chrome・msedgewebview2・dotnet・pwsh・pCloud・HP の各ツール | 数 KB から 30 MB。.NET Framework は書き込みも実行もできる領域を多く持つ |
| JIT を EXE に内蔵 | claude.exe（Electron のデスクトップ版と、Bun で固めた Claude Code の両方） | 書き込みも実行もできる領域が 300 個を超えるものもある。DLL の名前では見分けられなかった |
| JIT なし | explorer・SystemSettings・uihost の 3 つだけ | **どれも書き込みはできない**。4 KB が数個〜計 128 KB |

これを基準に、点を決めた。

| 兆候（JIT を持たないプロセスについて） | 点 |
|---|---|
| ファイルの裏付けが無く、**書き込みも実行もできる**領域がある | +30 |
| ファイルを写しただけの領域が、実行できるようになっている | +30 |
| ファイルの裏付けが無い実行可能な領域がある（書き込みはできない） | 点を付けず、情報として挙げる |

- 点は、その領域を持つプロセスの実行ファイルに付ける。根拠の文に、プロセス ID・個数・大きさ・先頭の番地を出す
- 書き込みのできない領域に点を付けないのは、explorer などが正規に持っているため
  （ウィンドウ処理の中継コードなど）。**書き込んだあとで保護を「実行のみ」に変える手口は、点が付かない**
- 「ファイルを写しただけの領域が実行できる」は、この PC では JIT の有無にかかわらず 0 件だった

**見えないもの**:

- **JIT を持つプロセスへのインジェクション**（ブラウザー、.NET のアプリ、Electron のアプリ）。区別する手がかりが無い
- **読み込んだ DLL の中身を、メモリ上で書き換える手口**。領域の種類はイメージのままなので、ここには出てこない。
  見つけるには、メモリの中身をディスク上のファイルと比べる必要がある
- **中身に実行ファイルの形（PE ヘッダー）があるかどうか**。中身を読めば、JIT を持つプロセスの中でも
  見分けられるようになるが、ほかのプロセスのメモリを読むことになる（§14）

採点の調整用に、コンソール版に一覧を出す入口を置いた。

```
pcmonitor --memory-map      プロセスごとに、該当する領域の個数・大きさと、JIT の手がかりを並べる
```

### 11.4 署名の検証の補足

**埋め込み署名が「無効」でも、カタログとパッケージを確かめる**（§5.4 の補足）。Windows 付属の

中身が書き換えられていれば、カタログにもパッケージの記録にも合わないので、ここで有効になることはない。

親子異常は 0 件、DLL の候補は 42 件（うち 40 件は 20 点で「低」。ほとんどが pCloud の同梱 DLL）。
残りの 2 件は 50 点で、直前のビルドでコンパイラーが `Temp` に写した xunit の DLL だった
（署名済みの `dotnet.exe` が、書き込める場所の新しい未署名 DLL を読み込んでいる。規則どおりの検知）。

あわせて確かめること:

- `System32` のファイルが「未署名」と出ていないこと（カタログ署名の検証が効いているか）
  → 確認済み。未署名 0 件、無効 0 件
- 通常権限と管理者権限の両方で最後まで走ること
  → 通常権限は確認済み。**管理者権限はまだ**（昇格の確認は本人が画面で行う）
- 何も入れていない状態の PC で、「高」が出ないこと（出るなら採点を見直す）
  → この PC では 0 件

画面の見え方は、ビルドして起動したものを本人が確認する。

## 13. 限界

- **カーネルレベルのルートキット**: 隠されたプロセスやファイルは見えない
- **正規ツールの悪用**: 署名済みのツールだけで組まれた侵入は、点が上がりにくい
- **正規プロセスへのインジェクション**: DLL として載せる形と、親が不自然な形は見える（§11.1、§11.2）。
  ファイルを介さずメモリに直接書き込む形は、JIT を持たないプロセスで、書き込みも実行もできる領域が
  残っているときだけ見える（§11.3）。ブラウザーや .NET のアプリの中は見えない
- **管理者でないと見えないプロセス**: 通常の権限では、この PC で 150 個のプロセスの DLL を確かめられなかった
- **ハードウェアのキーロガー**: ソフトからは検知できない
- **スナップショットであること**: 点検した瞬間に動いていないもの、張っていない接続は見えない

「何も出なかった」は「安全」を意味しない。画面にもそう書く。

## 14. 未決事項

- 採点の点数と境界（実機で試して調整する）。とくに **「低」が 400 件を超える**こと。
  署名済みの自動起動（サービス・ドライバー）が +10 で軒並み「低」になるため。
  一覧は危険度の高い順なので実害は小さいが、「低」の意味が薄い
- 管理者権限で最後まで走ることの確認（WMI イベント購読は、管理者でないと読めない）
- **ほかのプロセスのメモリの中身を読むかどうか。** いまは読まない。読めば、確保された領域に
  実行ファイルの形（PE ヘッダー）があるかを見られ、JIT を持つプロセスの中でも見分けられるようになる。
  一方で、点検ツール自身が「ほかのプロセスのメモリを読む」動きをすることになり、
  セキュリティ製品に止められたり、疑われたりしうる（とくに `lsass.exe`）。入れるなら対象と除外を先に決める
- ほかの利用者の `HKU\<SID>` の Run キーは見ていない（いまは HKLM と HKCU だけ）
- 定期実行して差分だけ通知する機能を入れるか
- 既知マルウェアのハッシュ一覧や YARA ルールとの照合を足すか
  （足すなら、一覧の入手元と更新のしかたを決める）
- インストーラーを作るか、ZIP の配布に留めるか
