# Security 設計書

常駐型のキーロガーとバックドアの「疑わしい候補」を洗い出す、Windows 用の点検ツール。

- 作成日: 2026-11-13
- 状態: 設計のみ（実装はまだ無い）

## 1. 目的と位置づけ

Windows Defender を**置き換えない**。Defender が見ない観点を補う点検ツールとする。

- Defender はシグネチャと挙動で「既知の悪いもの」を止める
- Security は「常駐している・通信している・署名が無い」といった**条件の重なり**を見て、
  人が確認すべきものを危険度順に並べる

判定は「疑わしい候補」までで、「これはウィルスだ」とは断定しない。
キーロガーもバックドアも、使う仕組みは正規ソフト（IME、AutoHotkey、リモートデスクトップ系）と
同じなので、仕組みだけでは区別できないため。

## 2. 範囲

### やること

| 段階 | 内容 |
|---|---|
| 第 1 段階 | 常駐箇所の点検、プロセスの署名と起動場所の点検、通信の点検、WPF 画面、許可リスト、書き出しと前回との差分 |
| 第 2 段階 | メモリの点検（インジェクションの痕跡）、読み込み DLL の点検、ETW によるキー入力 API の監視 |

### やらないこと

| やらないこと | 理由 |
|---|---|
| リアルタイム保護（開いた瞬間に止める） | カーネルのミニフィルタードライバーと Microsoft の署名が要る |
| 削除・隔離・プロセスの強制終了 | 誤検知で正規ソフトを壊す。ツールは「見つけて示す」まで |
| 検体のアップロード（VirusTotal など） | 手元のファイルを外部へ送ることになる。ハッシュをコピーして本人が調べる |
| カーネルレベルのルートキットの検知 | ユーザーモードからは、隠されたものが見えない |

## 3. 対象とする手口

### キーロガー

| 手口 | 第 1 段階での見つけ方 | 第 2 段階での見つけ方 |
|---|---|---|
| キーボードフック（`SetWindowsHookEx` の `WH_KEYBOARD_LL`） | 間接的な兆候のみ（下記） | ETW で設置の瞬間を捕まえる |
| ポーリング（`GetAsyncKeyState` を高頻度で呼ぶ） | 間接的な兆候のみ | ETW で呼び出し元を特定する |
| Raw Input の登録（`RegisterRawInputDevices`） | 間接的な兆候のみ | ETW で登録の瞬間を捕まえる |

設置済みのフックを列挙する公式 API は無い。第 1 段階では、次の兆候の重なりで候補に挙げる。

- 自動起動に登録されている
- ウィンドウを表示しないのに常駐している
- 未署名である
- ユーザーが書き込める場所（`AppData`、`Temp` など）から起動している

### バックドア

通信と常駐の両方が要るので、キーロガーより手がかりが多い。

- 未署名のプロセスが、ループバック以外でポートを待ち受けている
- 未署名のプロセスが、外向きの接続を持ち続けている
- 自動起動の登録が、スクリプト実行系の正規ツール（`powershell -enc`、`mshta`、`rundll32`、
  `regsvr32` など）を経由している
- システムのプロセス名を名乗っているが、置き場所が違う（`System32` 以外の `svchost.exe` など）

## 4. 全体構成

```
Security/
  ├─ Docs/design.md             この文書
  ├─ Security.sln
  ├─ src/
  │   ├─ Security.Core/         点検ロジック。UI に依存しない
  │   └─ Security.Wpf/          画面（WPF + ReactiveUI）
  └─ tests/
      ├─ Security.Core.Tests/   採点と解析の単体テスト
      └─ Security.Probe/        検知を実測するための無害な検証プログラム（§12）
```

| プロジェクト | TargetFramework | 備考 |
|---|---|---|
| `Security.Core` | `net9.0-windows` | Win32 API を P/Invoke で呼ぶ。Nullable `enable` |
| `Security.Wpf` | `net9.0-windows` | ReactiveUI は **23.2.28 に固定**。`StartupUri` は使わず `App.xaml.cs` で手動初期化 |

点検ロジックを `Core` に分けるのは、あとでコンソール版や定期実行（タスクスケジューラから
起動して差分だけ通知する）を足せるようにするため。

### Core の中の分け方

```
Security.Core/
  ├─ Collectors/     事実を集める（判断しない）
  │   ├─ PersistenceCollector   常駐箇所
  │   ├─ ProcessCollector       プロセス
  │   └─ NetworkCollector       通信
  ├─ Signing/        署名の検証
  ├─ Scoring/        集めた事実に兆候を付け、危険度を決める
  ├─ Allowlist/      許可リスト
  └─ Reports/        書き出しと差分
```

**集める**と**判断する**を分ける。採点の規則はあとで必ず調整することになるので、
事実の取得を巻き込まずに直せるようにしておく。

## 5. 点検項目（第 1 段階）

### 5.1 常駐箇所

| 箇所 | 読む場所 |
|---|---|
| Run / RunOnce | `HKLM` と `HKCU` の `Software\Microsoft\Windows\CurrentVersion\Run`・`RunOnce`。`WOW6432Node` 側も見る |
| スタートアップ フォルダー | ユーザーごと、および全ユーザー共通。`.lnk` はリンク先まで解決する |
| サービス | `HKLM\SYSTEM\CurrentControlSet\Services`。`ImagePath` と、`svchost` 経由なら `Parameters\ServiceDll` |
| タスクスケジューラ | Task Scheduler の COM インターフェイスで列挙し、実行するコマンドを取る |
| WMI イベント購読 | `root\subscription` の `__EventFilter`・`CommandLineEventConsumer`・`ActiveScriptEventConsumer`・`__FilterToConsumerBinding` |
| Winlogon | `Shell`・`Userinit` が既定値から変わっていないか |
| `AppInit_DLLs` | 値が入っていれば挙げる |
| IFEO | `Image File Execution Options` の `Debugger` 値 |

登録されたコマンドラインから**実行ファイルのパスを取り出す**処理が要になる。
引用符の有無、環境変数、`rundll32 xxx.dll,Entry` のような間接起動を解いて、
実際に動くファイルまでたどる。たどれなかったものは「解決できず」として挙げる（隠さない）。

### 5.2 プロセス

| 取るもの | 取り方 |
|---|---|
| 一覧と親プロセス | Toolhelp スナップショット |
| 実行ファイルのパス | `QueryFullProcessImageName`（`PROCESS_QUERY_LIMITED_INFORMATION` で足りる） |
| コマンドライン | WMI の `Win32_Process` |
| 表示中のウィンドウの有無 | `EnumWindows` と `IsWindowVisible` |
| 署名 | §5.4 |
| ファイルの作成日時・ハッシュ（SHA-256） | ファイルから |

### 5.3 通信

| 取るもの | 取り方 |
|---|---|
| TCP の待ち受けと接続（プロセス ID 付き） | `GetExtendedTcpTable`（IPv4 と IPv6） |
| UDP の待ち受け（プロセス ID 付き） | `GetExtendedUdpTable`（IPv4 と IPv6） |

スナップショットなので、**点検した瞬間に張っていない接続は見えない**。
一定間隔で通信するバックドアを見逃しうる。第 1 段階では「待ち受け」を主な手がかりとし、
外向き接続は補助に留める。

### 5.4 署名の検証

`WinVerifyTrust` を使う。**埋め込み署名だけでなく、カタログ署名も必ず確かめる。**
Windows 付属のファイルの多くはカタログ署名で、埋め込み署名を持たない。
これを見落とすと、`System32` の中身が軒並み「未署名」と出て、結果が使いものにならなくなる。

結果は 4 通りに分ける。

| 結果 | 意味 |
|---|---|
| 有効（Microsoft） | 署名が有効で、発行元が Microsoft |
| 有効（その他） | 署名が有効。発行元の名前を表示する |
| 無効 | 署名はあるが検証に失敗（改ざん・失効・期限切れ） |
| 無し | 署名が無い |

**署名が有効でも安全とは限らない**（正規ツールの悪用、盗まれた証明書）。
署名は「減点の材料」であって「無罪の証明」ではない。

## 6. 危険度の採点

事実に**兆候**を付け、点数を足して危険度を決める。点数は初期値で、実機で試しながら調整する。

| 兆候 | 点 |
|---|---|
| 署名が無効 | +50 |
| システムのプロセス名を名乗るが、置き場所が違う | +40 |
| 自動起動がスクリプト実行系の正規ツールを経由している | +40 |
| 署名が無い | +30 |
| ユーザーが書き込める場所から起動している | +20 |
| ループバック以外でポートを待ち受けている | +20 |
| 隠し属性が付いている、または拡張子が二重（`.pdf.exe` など） | +15 |
| 自動起動に登録されている | +10 |
| 外向きの接続を持っている | +10 |
| 表示中のウィンドウが無い | +10 |
| ファイルの作成日時が 7 日以内 | +10 |

| 危険度 | 点 |
|---|---|
| 高 | 60 以上 |
| 中 | 30〜59 |
| 低 | 10〜29 |
| 情報 | 9 以下 |

- 兆候は 1 つずつでは弱い。**重なったときに上がる**ように、単独で「高」になるものは作らない
- 「登録は残っているが、ファイルが無い」は点を付けず、情報として挙げる
- 同じ実行ファイルが常駐・プロセス・通信の 3 か所に出てきたら、**1 件にまとめて**兆候を合算する
  （パスで突き合わせる）。まとめないと、同じものが 3 行に分かれて危険度が低く見える

## 7. データモデル

```
Finding（1 件の候補）
  ├─ Path            実行ファイルのパス（まとめる単位）
  ├─ Sha256
  ├─ Signature       結果と発行元
  ├─ Indicators[]    付いた兆候（種類・点・根拠の文）
  ├─ Score / Level   合計点と危険度
  ├─ Persistence[]   どの常駐箇所に、どんなコマンドラインで登録されているか
  ├─ Processes[]     プロセス ID・親・コマンドライン・ウィンドウの有無
  └─ Endpoints[]     プロトコル・ローカルのアドレスとポート・相手先・状態
```

兆候には**根拠の文**を必ず持たせる（「`HKCU\...\Run` の `Updater` に登録」など）。
点数だけ出しても、人は確認のしようがない。

## 8. 画面

1 つのウィンドウに、上から「操作」「一覧」「詳細」を並べる。

```
┌──────────────────────────────────────────────────────────┐
│ [スキャン] [管理者として再起動]   種別 ▼  危険度 ▼  検索 │
│ 進捗: 通信を点検中…                 □ 許可済みも表示     │
├──────────────────────────────────────────────────────────┤
│ 危険度 │ 名前        │ 署名     │ 兆候            │ 点  │
│ 高     │ updater.exe │ 無し     │ 常駐 待受 未署名│ 70  │
│ 中     │ …           │          │                 │     │
├──────────────────────────────────────────────────────────┤
│ 詳細: パス / SHA-256 / 署名者 / 作成日時                 │
│ 根拠: ・HKCU\…\Run の「Updater」に登録                   │
│       ・0.0.0.0:4444 を待ち受け                          │
│ [ファイルの場所を開く] [ハッシュをコピー] [許可リストへ] │
└──────────────────────────────────────────────────────────┘
```

- **一覧**: 既定は危険度の高い順。種別（常駐・プロセス・通信）と危険度で絞り込める
- **詳細**: 選んだ項目の根拠を文で並べる
- **操作**: 「ファイルの場所を開く」「ハッシュをコピー」「許可リストへ追加」だけ。壊す操作は置かない
- **書き出し**: CSV と JSON
- **前回との差分**: 前回の結果と比べ、新しく増えた項目に印を付ける

スキャンは別スレッドで走らせ、途中で止められるようにする。項目ごとの失敗（権限不足など）は
全体を止めず、「この項目は点検できなかった」として画面に出す。

## 9. 権限

| 権限 | 見られる範囲 |
|---|---|
| 通常 | 常駐箇所の大半、自分のプロセス、通信の一覧 |
| 管理者 | 上に加えて、他ユーザーとシステムのプロセスのパス、一部のタスク、WMI イベント購読 |

- 通常権限でも起動でき、**見られる範囲だけ点検する**。マニフェストで昇格を強制しない
- 見られなかった項目は、件数とともに「管理者なら見られる」と表示する
- 「管理者として再起動」ボタンで昇格する

## 10. 保存するもの

置き場所は `%LOCALAPPDATA%\Security\`。どれも JSON（UTF-8、BOM 無し）。

| ファイル | 中身 |
|---|---|
| `allowlist.json` | 許可リスト |
| `last-scan.json` | 前回の結果（差分に使う） |

### 許可リスト

**パスとハッシュの組**で登録する。パスだけで許可すると、同じ場所のファイルを
差し替えられても気づけない。ハッシュが変わったら許可は外れ、
「許可済みだったが中身が変わった」として挙げる（更新でも変わるので、危険度は上げない）。

## 11. 第 2 段階

| 項目 | 内容 |
|---|---|
| メモリの点検 | `VirtualQueryEx` で、ファイルの裏付けが無い実行可能な領域を探す（インジェクションの痕跡）。JIT を使うプロセス（ブラウザー、.NET）で誤検知が出るので、除外の扱いを決めてから入れる |
| 読み込み DLL の点検 | 署名済みのプロセスに読み込まれた未署名の DLL |
| ETW によるキー入力 API の監視 | Win32k のプロバイダーで、`SetWindowsHookEx`・`GetAsyncKeyState`・`RegisterRawInputDevices` の呼び出し元を記録する。管理者権限が要る |
| 親子関係の異常 | Office からシェルが起動している、など |

⚠️ ETW のイベント番号と取れる項目は、**実機で確かめてから設計に書く**。
Windows の版で変わりうるので、記憶で決めない。

## 12. 確認のしかた

「動くはず」で済ませない。**無害な検証プログラム**（`tests/Security.Probe`）を作り、
実際に検知されることを実測する。

| 検証プログラムのふるまい | 期待する結果 |
|---|---|
| 未署名で、`HKCU` の Run キーに自分を登録する | 常駐の兆候が付く |
| 未署名で、`0.0.0.0` のポートを待ち受ける | 待ち受けの兆候が付く |
| ウィンドウを出さずに常駐する | ウィンドウ無しの兆候が付く |
| 上の 3 つを同時に行う | 1 件にまとまり、危険度が「高」になる |

検証プログラムは、終了時に自分の登録を消す。キー入力の取得は行わない。

あわせて確かめること:

- `System32` のファイルが「未署名」と出ていないこと（カタログ署名の検証が効いているか）
- 通常権限と管理者権限の両方で最後まで走ること
- 何も入れていない状態の PC で、「高」が出ないこと（出るなら採点を見直す）

画面の見え方は、ビルドして起動したものを本人が確認する。

## 13. 限界

- **カーネルレベルのルートキット**: 隠されたプロセスやファイルは見えない
- **正規ツールの悪用**: 署名済みのツールだけで組まれた侵入は、点が上がりにくい
- **正規プロセスへのインジェクション**: 第 1 段階では見えない（第 2 段階のメモリ点検の対象）
- **ハードウェアのキーロガー**: ソフトからは検知できない
- **スナップショットであること**: 点検した瞬間に動いていないもの、張っていない接続は見えない

「何も出なかった」は「安全」を意味しない。画面にもそう書く。
