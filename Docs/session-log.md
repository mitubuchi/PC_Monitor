## 2026-11-13

### 利用者

Windowsのウィルスチェックプログラムを書くことはできますか？

### Claude

はい、書けます。ただし「どこまでのものか」で現実味が大きく変わります。

**現実的に作れるもの（オンデマンドスキャナー）**
- **ハッシュ照合**: ファイルの SHA-256 を既知マルウェアのハッシュ一覧（MalwareBazaar などの公開データ）と突き合わせる
- **YARA ルール**: 公開されているルールセットでファイルの中身をパターン照合する
- **PE ファイルの静的解析**: 高エントロピーのセクション（パッカーの疑い）、怪しいインポート、署名の有無（Authenticode 検証）を調べる
- **常駐箇所の点検**: スタートアップ、Run キー、タスクスケジューラ、サービスに登録された実行ファイルを列挙し、未署名のものを洗い出す
- **Defender との連携**: AMSI や `MpCmdRun.exe` を呼び、判定は Defender のエンジンに任せる

**現実的でないもの**
- **リアルタイム保護**: ファイルを開いた瞬間に止めるにはカーネルのミニフィルタードライバーが要り、Microsoft の署名も必要です。
- **市販製品並みの検出率**: 検出力はシグネチャと解析基盤の継続運用で決まるので、個人のプログラムでは Defender の代わりになりません。

なので、「Defender を置き換える」のではなく「Defender が見ない観点を補う点検ツール」として作るのが筋です。たとえば未署名の常駐プログラムの洗い出しや、特定フォルダーの YARA スキャンです。

このマシンの環境なら C#（.NET 9）のコンソールアプリから始めるのが素直です。最初の一歩としては「指定フォルダーを走査し、ハッシュ照合・署名検証・エントロピー判定をして、結果を一覧で出す」ものを勧めます。

何を目的にしていますか（学習用、手元の PC の点検、特定のファイルの調査など）。それによって組み合わせる機能が変わります。目的が決まっていなければ、上の最初の一歩の構成で作り始めます。

### 利用者

特に常駐型で、キー入力などを、取得するとか
バックドア系のウィルスを検知する事はかのうですか？

### Claude

可能です。ただし、挙げられるのは「疑わしい候補」までで、「これはウィルスだ」と断定はできません。キーロガーもバックドアも、使う仕組みは正規ソフトと同じだからです（IME、AutoHotkey、リモートデスクトップ系など）。

#### キーロガーの検知

キー入力を取る手口は主に 3 つで、見つけやすさが違います。

| 手口 | 検知のしやすさ |
|---|---|
| キーボードフック（`SetWindowsHookEx`） | 設置済みフックを列挙する公式 API は無い。設置の瞬間なら ETW（Win32k プロバイダーの API 監査イベント）で捕まえられる見込みだが、実機での確認が要る |
| ポーリング（`GetAsyncKeyState` を高頻度で呼ぶ） | 同じく ETW で呼び出し元プロセスを特定できる見込み |
| Raw Input の登録 | 他プロセスの登録状況は直接読めないので、間接的な兆候で判断する |

間接的な兆候とは、ウィンドウを表示しないのに常駐している、未署名である、`AppData` や `Temp` から起動している、自動起動に登録されている、といった条件の重なりです。

#### バックドアの検知

こちらは通信と常駐の両方が要るので、キーロガーより手がかりが多いです。

- **通信**: プロセスごとの待ち受けポートと外向き接続を列挙し、未署名のプロセスが通信しているものを洗い出す。
- **常駐箇所**: Run キー、サービス、タスクスケジューラ、スタートアップ、WMI イベント購読、`AppInit_DLLs`、IFEO などを点検する。
- **プロセスの異常**: 署名済みプロセスに未署名の DLL が読み込まれている、ファイルの裏付けが無い実行可能メモリ領域がある（インジェクションの痕跡）、親子関係が不自然（Office から PowerShell が起動しているなど）。

#### 見つけられないもの

- **カーネルレベルのルートキット**: ユーザーモードのツールからは、隠されたものが見えません。
- **正規ツールの悪用**: 署名済みの PowerShell や正規のリモート管理ツールを使われると、署名検証をすり抜けます。
- **ハードウェアのキーロガー**: USB に挟む型は、ソフトからは検知できません。

#### 勧める形

C# のコンソールアプリで、常駐箇所・プロセスの署名・通信・メモリの異常をまとめて点検し、条件が重なったものを危険度順に一覧で出すスナップショット型が現実的です。ETW でのリアルタイム監視は、その上に第 2 段階として足せます（管理者権限が要ります）。

この構成でよければ、作り始めます。

### Claude

可能です。点検ツールは結果を見比べて判断する作業が中心なので、コンソールより WPF のほうが向いています。

#### 構成

- **`Seculity.Core`（点検ロジック）**: 常駐箇所・署名・通信・メモリの点検を UI から切り離して持ちます。あとでコンソール版や定期実行を足せます。
- **`Seculity.Wpf`（画面）**: ReactiveUI 23.2.28 で、他のプロジェクトと同じ作りにします。

#### 画面

- **スキャン実行**: ボタン 1 つで全項目を点検し、進捗を表示します。項目ごとの個別実行もできます。
- **結果一覧**: 危険度順に並べ、種別（常駐・通信・プロセス・メモリ）で絞り込めます。
- **詳細ペイン**: 選んだ項目について、なぜ疑わしいかの根拠を出します（未署名、`AppData` から起動、待ち受けポートあり、など）。あわせてファイルの場所・署名者・ハッシュも表示します。
- **許可リスト**: 確認して問題なかったものを登録し、次回から表示を抑えます。これが無いと毎回同じ誤検知を見ることになります。
- **書き出し**: 結果を CSV / JSON で保存し、前回との差分（新しく増えた常駐項目）を見られるようにします。

#### 先に決めておく点

- **管理者権限**: 他プロセスのメモリや読み込み DLL を見るには昇格が必要です。通常権限でも起動でき、見られる範囲だけ点検する作りにします。全項目を見たいときは「管理者として再起動」ボタンを使います。
- **削除や強制終了はしない**: 誤検知で正規ソフトを壊す危険があるので、ツールは「見つけて示す」までにします。操作は「ファイルの場所を開く」「ハッシュをコピー」程度に留めます。
- **画面の確認**: こちらでビルドと起動まで行い、画面の見え方はご自身で確認していただきます。

まず第 1 段階として、常駐箇所・プロセスの署名・通信の点検と WPF 画面までを作るのが妥当です。メモリの点検と ETW でのキー入力 API 監視は第 2 段階にします。

「作って」と言っていただければ、`D:\Claude\Seculity` に第 1 段階を作り始めます。

これまでの話に加えて、設計書で新しく決めた点は次のとおりです。

- **採点**: 兆候ごとに点を付け、合計で高・中・低・情報に分けます。単独で「高」になる兆候は作らず、重なったときだけ上がるようにしました。点数は初期値で、実機で試して調整します。
- **1 件にまとめる**: 同じ実行ファイルが常駐・プロセス・通信に出てきたら、パスで突き合わせて 1 件にします。
- **カタログ署名の検証**: Windows 付属のファイルの多くは埋め込み署名を持たないので、カタログ署名も確かめます。これを省くと `System32` の中身が軒並み「未署名」と出ます。
- **許可リストはパスとハッシュの組**: パスだけで許可すると、ファイルを差し替えられても気づけないためです。
- **確認用の検証プログラム**: Run キーへの登録やポートの待ち受けをする無害なプログラムを作り、実際に検知されるかを実測します。キー入力の取得はさせません。
- **検体のアップロードはしない**: VirusTotal などへの送信は入れず、ハッシュをコピーしてご自身で調べる形にしました。

ETW のイベント番号と取れる項目は、実機で確かめてから設計書に書き足します。未決事項（定期実行、ハッシュ一覧や YARA との照合、配布形態）は §14 にまとめてあります。

#### 他の PC での手順


#### 渡るもの、渡らないもの

- **渡らない**: 実測の結果（`artifacts/`）。git に入れていないので、必要なら向こうで取り直します。

会話が渡らないので、追加したい機能がもう決まっているなら、向こうのセッションの最初に内容を伝える必要があります。ここで内容を教えていただければ、設計書への追記案としてまとめて push しておくこともできます。
